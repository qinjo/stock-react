> 样本票：**600519 贵州茅台**（若无特别说明）。当前最新报告期 = **2026 中报**，最新交易日 = **2026-09-18**。

## 0. 核心结论（TL;DR）

1. **P0 财务基本面已完全解决，且不需要 push2。** `datacenter-web.eastmoney.com` 的 `RPT_F10_FINANCE_MAINFINADATA` **一次请求**就能拿到营收/归母净利/扣非净利/同比增速/ROE/毛利率/净利率/资产负债率/EPS/BPS/每股经营现金流（最近 103 个报告期，取 8 期即可）。
2. **P0 历史估值分位已完全解决。** `RPT_VALUEANALYSIS_DET` 对单票返回**日度 PE_TTM / PB_MRQ / PS_TTM / PCF / PEG 历史序列**，600519 实测拿到 **2116 个交易日（2018-01-02 → 2026-09-18，约 8.6 年）**。分位数可直接算，无需外部数据拼接。
3. **最重要的架构发现：东财的反爬是「按域名隔离」的，不是全站 IP 封禁。**
   在 `push2` / `push2his` 已经返回 `HTTP 000（空响应）` 的封禁窗口内，`datacenter-web` 与 `emweb` **依然 200 正常返回**（已实测）。
   → 结论：**基本面数据走 datacenter-web，完全不与行情接口争抢那点反爬额度**，两条链路要分开限流。
4. **push2 封禁阈值实测：约 10 次密集请求。** 带 `User-Agent` + `Referer` 连续 10 次（4 次间隔 4s + 6 次无间隔突发）全部成功；第 11 次起整段返回 `HTTP 000`，且**带不带 `ut=`/`Referer` 都失败**（已做 A/B 排除，见 §5.3）。
   恢复时间：约 90 秒后**单次**成功，紧接着的请求又失败 → 恢复是**渐进/多边缘节点**的，不能假定"等 1 分钟就满血复活"。
   **注意：`ut=` 与 `Referer` 不是绕过反爬的开关，但也不应省略**（web 前端自己带）。
5. **push2 有免封替代品**：指数日 K 用腾讯 `web.ifzq.gtimg.cn`（实测 `sh000001`/`sz399001`/`sz399006` 全部可用）。
6. **全部接口均免 key**，`datacenter-web` 与 `qt.gtimg.cn` 实测返回 `Access-Control-Allow-Origin: *`。

## 2. 接口详列

### 2.0 通用约定（所有 `datacenter-web` 接口共用）

```
GET https://datacenter-web.eastmoney.com/api/data/v1/get
  ?reportName=<报表名>
  &columns=ALL            # 或 columns=字段1,字段2（逗号分隔，可显著减小响应）
  &filter=<过滤表达式>     # 见下
  &pageNumber=1
  &pageSize=<N>           # 实测 800 可用
  &sortColumns=<字段>&sortTypes=-1
  &source=WEB&client=WEB
```

**filter 表达式语法（实测确认）：**
- 多个条件是**括号并置**（隐式 AND），不是 `and`：
  `filter=(BOARD_CODE="016165")(TRADE_DATE='2026-09-18')`
- 字符串用**双引号**（股票代码/板块代码）或**单引号**（日期）都可，但日期实测必须用单引号。
- 日期格式 `YYYY-MM-DD`。
- ⚠️ **坑**：不同 reportName 的"股票代码"字段名不一样！同一个接口族里混用
  `SECURITY_CODE`（6 位纯代码，如 `600519`）和 `SECUCODE`（带后缀，如 `600519.SH`）。
  用错会返回 `{"message":"XXX列不存在","code":9501}` 或 `返回数据为空(9201)`。
  实测对照：`RPT_LICO_FN_CPD`/`RPT_VALUEANALYSIS_DET` 用 `SECURITY_CODE`；
  `RPT_F10_FINANCE_MAINFINADATA`/`RPT_F10_EH_*`/`RPT_LIFT_STAGE` 用 `SECUCODE`。
- 东财自家 JS 里 `RPTA_WEB_RZRQ_GGMX` 有一个 **`fliter=` 拼写错误**（不是 `filter`），照抄前端会踩坑。

**反爬实测（重要）**：对 `datacenter-web` 累计发出 **20+ 次请求**，含 **8 次无间隔并发**，**全部 HTTP 200**，单次耗时 **0.08–0.25s**，**未触发任何限流**。
→ 该域名与本项目已知的 push2 反爬**完全无关**。

1. **`MLR` 不是毛利率，是毛利额（元）！** 实测 `MLR = 81229498398.6`（812 亿），而真正的毛利率是 `XSMLL = 89.56`。命名反直觉，极易误用。

   已精确验证：`NETCASH_OPERATE(70690750119.06) / OPERATE_INCOME(90703260964.48) = 0.77936283`，

   展示给 LLM 时需 `×100`。
3. 财务数据是**年内累计（YTD）口径**，不是单季。2026 中报 = H1 累计。要单季需自行差分。
4. `STAFF_NUM` 在 600519 返回 `null`（该字段并非所有票都填）。
5. **交叉校验锚点**（可用来单测本适配器）：`每股经营现金流 56.54890853726 × 总股本 1250081601 = 706.91 亿`
   = 现金流量表的 `NETCASH_OPERATE / 1e8`。两个接口能对上，说明单位都是"元、不缩放"。

- `pageSize=800` 单页 ≈ **3.3 年**（实测 2023-06-06 → 2026-09-18），**1 次请求 / ~218 KB**
- 取 3 页 ≈ **8.6 年全历史**（2116 个交易日，2018-01-02 起）
- `PE_TTM` / `PB_MRQ` 均为**已算好的倍数值，不需缩放**

**分位计算公式**：`分位 = 100 × (序列中小于当前值的个数) / 序列长度`

**本次实测结果（600519，截至 2026-09-18，PE_TTM=19.30 / PB_MRQ=6.25）**

| 窗口 | 样本天数 | PE 区间 (min–max) | PE 中位数 | **PE 当前分位** | PB 中位数 | **PB 当前分位** |

——**"估值是高是低"这个问题现在可以定量回答。**

### 3.2 备选路径：价格 + 财务自算（不推荐，但可行）

`PE_TTM ≈ 总市值 / 归母净利TTM`，`PB ≈ 总市值 / 归母净资产`。

- 历史价格：`push2his kline/get`（`fqt=1` 前复权）或腾讯 `fqkline`（免封）
- 历史 EPS/BPS：`RPT_LICO_FN_CPD` 的 `BASIC_EPS` / `BPS`，或 `MAINFINADATA` 的 `EPSJB` / `BPS`（季度频）
- 总股本：`TOTAL_SHARE`

**为什么不推荐**：
1. 财务是**季度频**，两个报告期之间 PE 会变成阶梯状，而真实 PE 是每日连续变化的；
2. TTM 净利需自行做 4 季滚动（且要处理 YTD 累计口径 → 单季差分）；
3. 前复权价格 × 股本 ≠ 当日真实总市值（复权因子与股本变动会引入误差）；
4. 直接接口已经**免费、精确、8.6 年、3 次请求**，没有理由自算。

> **唯一需要自算的场景**：想要 `PE_TTM` 之外的口径（如剔除商誉的 PB、EV/EBITDA）——那些没有免费日度序列。

### 3.3 局限与坑

- `PB_MRQ` 是**最新报告期**口径：在季报发布前后会发生**跳变**（分母换期），分位计算会受此影响；对比"近 1 年"时尤其明显。
- `PE_TTM` 在**亏损期**为负值。分位计算前必须**决定是否剔除负值**——本次实测中 `白酒Ⅱ` 19 只里有 5 只 PE 为负或无值。建议：剔除 `PE_TTM <= 0` 后再算分位（本次演示代码已剔除）。
- 历史区间起点 2018-01-02（接口上限），**做不了"近 10 年"**。
- `CLOSE_PRICE` 是**不复权原价**，别拿它去算收益率。

### 4.2 请求成本与限流策略（关键）

- **1–11 全部走 `datacenter-web`**：实测 **20+ 次请求全 200，8 次并发不限流，无封禁**。
  → **这 11 个接口彼此之间不需要间隔**，可以并发打。
- **只有第 12 项（资金流）碰 push2**。push2 实测约 **10 次密集请求后封禁**，因此：
  - **把 push2 的额度全部留给资金流**（行情快照/日 K/指数都已能由腾讯免封覆盖）；
  - 指数 K 线改用腾讯 → **push2 每票只剩 1 次请求**，在 10 次阈值内非常安全；
  - 必须做**进程级串行 + 节流**（项目已有 `rate-limit.ts`），建议 push2 最小间隔 **500ms–1s**、全局并发 1；
  - 一旦拿到 `HTTP 000 / 空响应`，**立即熔断整个 push2 链路并降级腾讯**，不要重试——重试只会延长封禁。
- **缓存策略**：第 1、2、6–11 项是**季度更新**数据，按报告期缓存即可；
  第 3 项（PE/PB 序列）**每日更新**，按交易日缓存（每天 1 次）；
  第 5 项（两融）每日更新；第 4 项按交易日缓存。
  → 稳态下每票每天只需刷新 **第 3、5 项**，其余命中季度缓存。

## 7. 给本项目的一条落地建议

当前 `backend/src/eastmoney.ts` 只用了 `push2 stock/get` + `push2his kline/get`，两个都在**同一个被封的域**上，且**每次分析都要打**——这正是"6 次就断"的根因。

建议拆成两条链路：

1. **`datacenter-web` 链路（新增，不限流）** → 承担全部 P0 基本面 + 估值分位 + 两融 + 事件（§4.1 的 1–11 项），并发无障碍。
2. **`push2` 链路（保留，严格节流）** → 只留给**当日实时快照**（必须实时）和**主力资金流**（无替代）；
   **日 K 与指数 K 线全部迁到腾讯**（`fqkline`，已实测可用），把 push2 每票请求数从 3 降到 1–2。

这样每票每次分析的 push2 请求从"至少 3 次"降到"1–2 次"，落在实测的 ~10 次安全阈值内，
而 Push 2 封禁时，**基本面分析完全不受影响**（已验证 datacenter-web 在封禁期间照常 200）。
