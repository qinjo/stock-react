# 0001 — A 股数据源主备策略

- **状态**：已采纳
- **日期**：2026-08-30
- **相关**：规格 issue #1（数据源决策 Q11「东财单源+缓存」）、工单 T2（#3）

## 背景

规格最初决定「东财单源 + 后端缓存」，理由是免 key、CORS 可用、字段一站式。落地 T2 时实测发现两个无法在代码层绕过的数据源问题：

1. **东财行情接口（push2 / push2his）有 IP 级反爬**：约 6 次密集请求后整段断连，返回空响应（curl 直连同样 `Empty reply from server`），并非请求头或参数问题。单源时页面直接不可用。
2. **东财 suggest 搜索接口对服务端请求结构性失效**：同一 URL 下，它只对 curl 式请求返回股票代码表（`QuotationCodeTable`），对 Node/浏览器请求返回股吧用户搜索（`result.passportWeb`）；且行为不稳定（同一请求头短时间内两种结果都出现过），疑似 TLS 指纹分流，无法在 Node 端可靠复现。

## 决策

1. **行情（实时快照 + 日 K）**：**东财为主、腾讯为备**，自动降级。
   - 主源东财：字段最全（含成交额、振幅、换手率）。
   - 备源腾讯：`qt.gtimg.cn`（实时，GBK 编码）与 `web.ifzq.gtimg.cn`（日 K，UTF-8）。
   - 触发条件：主源抛错即降级；**非法输入不降级**（两源结论相同，重试无意义）。
   - 降级事件通过日志钩子 `setDegradeLogger` 上报，便于观测主源健康度。
2. **搜索**：**腾讯 smartbox 为唯一源**（`smartbox.gtimg.cn/s3/`）。东财 suggest 不作为搜索源。
3. **单位口径统一**：腾讯的成交额（万元）与市值（亿元）在适配层换算为「元」，与东财一致，使上层无需感知来源差异。
4. **两源互不交叉校验**：不做双源比对打分（保持规格「不做冗余校验」的意图），降级仅用于可用性兜底。

## 后果

**收益**
- 单源反爬不再导致页面不可用；实测东财封禁期间链路自动切腾讯并返回完整数据。
- 两源数据实测一致（同一交易日 OHLCV 逐字段相同），交叉验证了各适配器的解析正确性。

**代价与约束**
- 维护两套适配器（字段索引、编码、列序各不相同）；腾讯不返回成交额/振幅/换手率，降级时这些字段为 `null`，UI 必须以「—」容错。
- 腾讯实时接口是 GBK 编码，需显式 `TextDecoder("gbk")`；相关 fixture 以原始字节入库以覆盖解码路径。
- 腾讯字段索引经与东财 fixture 逐值对照确认，**若腾讯调整字段顺序，测试会失败**——这正是保留 fixture 测试的目的。

**未采纳的替代方案**
- 仅等东财解封：反爬随时会再触发，可用性无保障。
- 引入付费 key 数据源（Twelve Data / Finnhub）：与「免 key 小项目」定位不符，留待需要美股或更高稳定性时再评估。
- 用 Node 的 http2/自定义 TLS 指纹去复现东财 suggest 的 curl 行为：脆弱且与运行时耦合，不值得。
