# 0004 — 全市场筛选器的数据层

- **状态**：已采纳
- **日期**：2026-09-30
- **相关**：规格 [A股短线筛选器](../spec-screener.md)（issue #8）；ADR-0001（行情数据源主备，本 ADR 在主备关系上**部分取代**它）；ADR-0002（提示词工程，本 ADR 在"模型失败怎么办"上给出**相反**的取舍）；`_research/短线操盘技法-选股规则提炼.md`（规则来源）；参数表附件 [`docs/screener-params.md`](../screener-params.md)

## 背景

要给「短线筛选器」筛出候选，就必须**在全市场（约 5900 只）上算均线**——因为源书的核心选股条件就是「收盘价 > MA100」。这与 `docs/spec.md` 原本的两条明文约束直接冲突：

> Out of Scope：**自行搭建数据仓储或全市场数据抓取（避免东财反爬风险）**
> Further Notes：东财有 IP 级反爬……本项目单票低频 + 缓存策略天然规避；**严禁后端扇出轮询**

于是本 ADR 要回答的其实是一个问题：**在不触发封禁的前提下，让一本书的规则真的跑在全市场上，需要付出什么。**

为此做了三轮实测（2026-09-29 / 09-30），结论有相当一部分与仓内既有笔记相反。

### 实测一：密集请求会触发封禁（**不是域名不可达**）

> **2026-09-30 的重要更正。** 本节原标题是「东财 push2 家族不可用，但是按域名隔离」。
> 后续复核证明**那个因果判断是错的**，详见本节末的「更正」小节。
> 下面的原始实测记录保留不动——**数据没错，错的是当时对数据的解释。**

| 域名 | 结果 |
|---|---|
| `push2` / `push2his` / `82.push2` / clist | ❌ TCP+TLS 通、**服务端不发任何响应即关闭**（curl `Empty reply`，延迟 0.07–0.16s，无 403/429/502） |
| `datacenter-web.eastmoney.com` | ✅ 200 / 0.14s |
| `qt.gtimg.cn` / `web.ifzq.gtimg.cn`（腾讯） | ✅ 正常 |

封禁时间线（实测）：

| 时刻 | 请求 | 结果 |
|---|---|---|
| 19:38 | clist `pz=3` | ✅ 200 |
| 19:39:05 | clist `pz=100` + 27 字段 | ❌ 首次尝试即断 |
| 19:43:50 | clist `pz=3` | ✅ ban#1 结束，历时 **≈4.3 分钟** |
| 19:44:23 | clist **`pz=6000`** | ❌ **0.083 秒**立即断，随后连 `pz=3` 都失败 |
| 19:54:37 | clist（静默 5 分钟后） | ❌ 仍断，**ban#2 ≥ 10.2 分钟** |
| 19:54:53 | **`push2his` kline** | ❌ —— **封禁已蔓延到 push2his** |

三条对仓内笔记的修正：

1. **「≥2 分钟恢复」低估了**：ban#1 ≈ 4.3 分钟，ban#2 ≥ 10.2 分钟且仍在持续，重复违规似**升级惩罚**。
2. **编号镜像同样被封**（`82.push2`、`push2delay`）→ 是 **IP 级，不是 host 级**。
3. **`push2his` 只是短暂隔离**：ban#1 期间还活着，ban#2 就死了。所以"东财主源 + 腾讯备源"的降级策略在密集场景下会**两个源一起没**。

> **一处事实更正**：调研中途曾判断"东财被我们自己的探测搞成全局封禁"。实测证明是**按域名隔离**——`datacenter-web` 在两个封禁窗口内 4 次探针全部 200。当时那句判断是**说重了**，现有应用的基本面面板从未受影响。

#### 更正（2026-09-30）：把两件事拆开，并撤回"域名不可达"的结论

上面的时间线里其实有**两组独立的证据**，当时被合并成了一个结论：

| 证据 | 说明什么 | 现在是否成立 |
|---|---|---|
| `pz=3` 通 → `pz=100` 即断 → 封禁后连 `pz=3` 也失败 → 重复违规惩罚升级 | **密集请求触发限速/封禁，且会蔓延到同 IP 的其它东财主机** | ✅ **成立**，这才是设计动机的真正依据 |
| `datacenter-web` 在封禁窗口内仍 200 | 当时解释为"按域名隔离的 ACL" | ⚠️ 观察属实，但**解释不成立**（更可能是各主机限速桶不同） |
| `push2` 在 curl 下 `Empty reply` | 当时解释为"服务端不发响应即关闭" | ❌ **不成立**，见下 |

**反例（2026-09-30 实测，同一 URL `push2.eastmoney.com/api/qt/stock/get?secid=1.600519`，各打 5 次）：**

```
Node fetch（应用内实际使用的客户端）：  5/5 成功  http=200 bytes=119
curl：                                1/5 成功（另 4 次连接失败）
```

**push2 是可用的。** "Empty reply" 更像是**探测客户端（curl）与该端点之间的握手差异**，
而不是服务端封锁。佐证：**应用自己的数据层一直是"东财为主、腾讯为备"，
而单票分析长期工作正常**——若 push2 真的永久不可达，那条主源路径早就没人发现了。

**这一更正不改变任何设计决策**，但**改变了它们的理由**：

- 「必须建本地库、每日只发十余个批量请求」的理由**不是**"域名不可达"，
  而是**"密集请求会触发封禁（实测 `pz=100` 即断，ban 4~10 分钟且惩罚升级）"**——
  这条依然成立，而且它本来就写在时间线里。
- 全市场扫描仍需数千次请求 → 依然不可行 → 本地库的结论不变。

**留给后人的提醒**：若将来要重新评估数据层，
请用**与应用相同的客户端**（Node `fetch`）去探测，而不是 curl——
否则会把客户端差异误读成服务端封锁。这正是当年那次误判的成因。

### 实测二：腾讯批量快照是唯一零限流的全市场通道

`https://qt.gtimg.cn/q=<codes>`：单请求 600 码返回 513 条有效（249KB / 0.080s），本会话多次批量请求**零限流**。→ **约 12 个请求覆盖全市场**。

其中一条是**单位陷阱**（连接口既有实现也中招）：

> **科创板（sh688/sh689）返回的成交量是「股」，其余板块是「手」。**
> 判定依据：对 4 只科创板标的做 `成交额 ÷ (成交量 × 100 × 现价)` 全部 ≈0.01，其余板块 ≈1.0。

不换算的后果极隐蔽：价格与成交额都对，只有成交量差两个数量级，而均线照样算得出来。

### 实测三：一次性 bootstrap 可以零东财请求

社区维护的 Qlib 格式 dump（`chenditc/investment_data`，每日重建）：

- 566,855,613 字节，sha256 `0756a5b7…13f65` **与发布方 manifest 逐位一致**
- 6,163 只标的（含北交所 598 只）、6,481 个交易日、10 个字段
- **纯 Node 可解析**：`.bin` 是 `float32[]`，元素 0 是日历起始索引，**没有数量字段**（`count = 字节数/4 − 1`）
- 原始价 = `close / factor`，已与 BaoStock / 腾讯 / 新浪三个独立源交叉验证到小数点后 4 位

## 决策

### 1. 建立本地日K库，产品形态是"离线 bootstrap + 每日增量"

- 库：单文件 SQLite（`node:sqlite`，Node 22 内置，**零新增依赖**），`code`/`date` 用 INT + `WITHOUT ROWID` 主键，实测约 70 B/行。
- **bootstrap**：下载上述社区 dump，**URL 与 sha256 一起钉死**；校验失败即明确报错、绝不写库。因上游每日重建、摘要每日变化，默认锚定的是**发布方 manifest 的 sha256**，需要完全可复现时再用 `--expect-sha256` 加钉一层。
- **每日增量**：腾讯批量快照，约 12–16 个请求、串行、请求间 `sleep`，**没有任何逐票扇出**。
- 全市场遍历在**本地**完成，线上外呼量从"5900 次"降到"十余次"。

### 2. 复权口径：存不复权价 + 因子，指标算在**后复权**序列上

`不复权` 是各数据源的默认口径；`factor` 由 dump 提供。关键是**不能用前复权**：

- `qfq = hfq / K`（K 为每股常数）→ 均线金叉/死叉的**时点与排序在两种口径下完全相同**，因此用后复权不会丢信息；
- 但**前复权不是增量稳定的**：每发生一次除权，整段前复权历史会被**追溯改写**，已算好的指标与缓存会被静默作废；
- **后复权是追加稳定的**：追加今天永远不改昨天。

同时，涨停判定、缺口、结构位、止损位这些"交易所价格空间"的概念，一律留在**不复权**口径上算。

### 3. 除权检测：用快照的「昨收」与库内收盘比对，只刷新该票的因子

快照的「昨收」是交易所口径的**除权后昨收**。与库内不复权收盘不等即成事件，此时把新 bar 的因子按 `库内昨收 ÷ 快照昨收` 放大，后复权序列保持连续，**历史 bar 的因子不动**。

前提是库内最后一根必须是快照日的**上一个交易日**。为此从**指数日线**建立真实交易日历（不自己算周末与节假日——调休会让"周一至周五"的直觉错一天）。不足以判定时**宁可标为"未判定"并如实上报，也不猜**：把普通涨跌误判成除权会按错误倍数改因子，而改完之后价、量、额全都"看起来正常"，只有均线悄悄偏了。

### 4. 主备关系反转：全市场场景下腾讯是主源

ADR-0001 定的是"东财主 + 腾讯备"，那是**单票低频**场景下的结论。全市场扫描下：

- 东财 push2 家族不可达且惩罚升级 → 不能作为主力；
- 腾讯批量是唯一实测零限流的通道 → **并列主源**；
- 东财 `push2his` 降级为"短名单专用的历史补齐通道"，绝不用于全市场；
- 东财 `datacenter-web` 与 push2 按域名隔离，可继续承担基本面取数。

### 5. 大模型失败时的取舍：筛选器**降级**，单票分析**abstain**

这与 ADR-0002 的取舍**刻意相反**，且必须在契约上可区分：

| | 单票分析 | 短线筛选器 |
|---|---|---|
| 模型的角色 | **主体**（评级/理由/报告都由它产出） | **可选的复核层**（只在同档内排序 + 写理由） |
| 失败时 | **abstain**（明确"分析失败"，不硬凑） | **降级**：照常返回规则结果，标注"未经 AI 复核" |
| 理由 | 模型缺席时结果没有意义 | 规则命中、档序、止损位、仓位**全部来自确定性计算**，模型挂掉丢的只是"复核" |

### 6. 本地库与 bootstrap 产物不进版本库

`backend/data/` 是可再生的构建产物（约 640 MB），已加入 `.gitignore`。

## 后果

**收益**

- 全市场筛选的线上外呼量约 16 次/天，**零逐票扇出**，与封禁风险解耦；
- 书的规则（`MA100`、低位 123、缺口、涨停位置）第一次真的跑在全市场上；
- 复权口径统一后，除权不再静默污染均线；实测 42 只除权股的后复权涨幅一致地高于不复权（股息被加回），无极端值；
- 数据可复现：锚定 sha256 + 交易日历来自真实指数日线。

**代价与风险**

- **引入本地仓储**，与 `docs/spec.md` 原 Out of Scope 冲突 → 已在该文档中修订；
- **依赖第三方社区 dump**：它每日重建、URL 可能变化、字段语义靠实测而非官方文档。缓解：sha256 钉死 + 三源交叉验证 + 全市场 VWAP 恒等式自检（`npm run verify:kline`）。若上游停更，降级路径是走 `datacenter-web` 按交易日取收盘价（只有收盘价，无 OHLC）；
- **腾讯是唯一实测零限流的通道**，成为单点。它的批量接口没有公开承诺，需持续观察；
- 库约 640 MB，bootstrap 需下载 541 MB 归档（约 40 秒）。

**后续若要做的事**

- 增量目前只能补"当天"：若库落后多个交易日，中间缺口无法用快照补齐，只能重新 bootstrap（已在增量里如实提示）；
- `datacenter-web` 在持续数千请求下的行为未验证（实测只发了约 10 次间隔请求）。
